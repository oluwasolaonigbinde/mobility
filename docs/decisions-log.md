# Client Decisions — Mobility AdTech Platform

The single decisions doc, in two parts. **Part 1** is the append-only log of
confirmed product decisions (D-numbers) in the order they were made — newer
rows supersede older ones where they conflict; never edit history. **Part 2**
is the *current* status of every questionnaire item Q1–Q34 with its adopted
direction and divergence guard (formerly `docs/adopted-decisions.md`, merged
4 Aug 2026 — stale references to that filename resolve here).

This is the **formal record**. For what the client wants now, topic by topic
in plain language, read [client-decisions.md](client-decisions.md); every
current rule there cites the D-row or Q-row here that governs it.

How change flows through the doc system: the request is recorded in
[requests.md](requests.md) → a client decision that changes product behaviour,
money, privacy, eligibility or security gets a new Part 1 row here, the
matching Part 2 status update, the topic update in `client-decisions.md` and
the `docs/architecture.md` amendment, all in the same commit → agents build to
the amended architecture → the request is marked done. Scope baseline: the client proposal
(`docs/Mobility_AdTech_MVP_Proposal_5_Month_Retargeting.docx`, D11), as
superseded by later direct client and project-owner decisions—currently D18–D25—where they
conflict.

   governing D-row (`D18`, plus `D20` for Q11/Q24/Q30), plus any
   implementation-specific D-row.
2. A future client change appends a superseding row to Part 1, updates the Q
   row here, and amends `architecture.md` in the same change (architecture §1).
3. An ADOPTED row never weakens an architecture invariant. Where this file and
   `architecture.md` conflict, the architecture doc wins — flag the conflict
   instead of building.

### Cross-cutting dependency notes

- **Q14 → Q28**: invoice engine and external-quotation capture build now;
  issuing real invoices waits on the remaining statutory company facts.
- **Q11 → Q31**: segment aggregation builds now; export and aggregate
  geographic/time/context activation remain disabled until legal sign-off.
  Direct push also requires `EXT-AD-PLATFORM`; person-level exposure
  retargeting is outside the pilot per D20.
- **Q23/Q27**: owner-driver-only does not remove the payee abstraction; live
  automated transfer additionally requires `EXT-DISBURSEMENT-PROVIDER`.
- **Q13 vs D1**: D1 (operator-led onboarding) now applies to advertisers/orgs
  only; drivers self-register per Q13. Cite both when touching onboarding.
- **Q10 vs D11**: D18 is later direct client authority. Pilot delivery is the
  screen-on installable PWA; the native background-tracking app is post-pilot.
